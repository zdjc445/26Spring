## 一、课程组织框架

这门课的整体主线不是单纯讲“如何使用 AI 写代码”，而是围绕 AI 时代的软件工程能力展开：

```text
AI 协作方法
→ 软件工程基础与项目管理
→ 需求工程
→ 体系结构设计
→ 详细设计
→ 代码设计、构造、测试与重构
→ 全学期团队项目留痕评价
```

课程核心范式是：

```text
提示 → 生成 → 审查 → 优化
```

其中，“审查”和“工程判断”是课程重点。课件多次强调：AI 可以生成初稿，但不能替代工程师对需求、设计、代码、质量和风险的判断。

### 5. 构造、代码设计、测试与重构

对应课件：

- `代码设计.pdf`
- `软件构造.pdf`

主要内容：

- 代码可读性：布局、命名、注释、Javadoc。
- 代码可维护性：小型任务、复杂决策、数据使用、明确依赖。
- 契约式设计、断言、防御式编程。
- 软件构造活动：详细设计、编程、测试、调试、代码评审、集成与构建、构造管理。
- 调试：重现问题、定位缺陷、修复缺陷。
- 代码评审：正式评审、轻量级评审、结对编程。
- 重构：不改变外部行为，改进内部结构。
- 坏味道：过长方法、大类、过多参数、重复代码、过多注释等。
- TDD：Red、Green、Refactor。

这一模块把设计原则落到代码层面，强调可读、可维护、可靠和可测试。

## 三、重点名词解释

### 课程与 AI 协作

| 名词 | 解释 |
| --- | --- |
| K-A-S-D | 课程评价框架。K 是知识，A 是 AI 协作与判断，S 是工程技能，D 是过程与态度。 |
| 三轨重构 | 以 AI 为参照，把知识点分为压缩区、强化区、新增区。AI 可辅助的内容压缩，人类判断相关内容强化，AI 时代新能力新增。 |
| Prompt Engineering | 提示词工程。通过结构化提示控制 AI 输出，课件公式为：角色 + 任务 + 约束 + 格式。 |
| AI 输出审查 | 对 AI 生成内容进行人工检查，重点识别错误、歧义、遗漏、冲突、幻觉和不符合工程约束的部分。 |
| Human-in-the-Loop | 人在环。AI 负责生成或辅助分析，人负责审查、决策和承担责任。 |

### 软件工程基础

| 名词 | 解释 |
| --- | --- |
| 软件 | 现代扩展定义为程序、数据、文档和知识的集合。 |
| 软件工程 | 将系统化、规范化、可量化的方法应用于软件开发、运行和维护。 |
| 软件危机 | 软件规模和复杂度增长后，传统个人式开发难以控制进度、成本、质量和维护问题。 |
| 项目 | 为创建唯一产品、服务或成果而进行的临时性工作。 |
| 铁三角 | 项目管理中的范围、时间、成本约束，目标是在约束下交付质量。 |
| 风险管理 | 对不确定事件及其影响进行识别、分析、排序、应对和监控。 |
| SQA | 软件质量保障，包括代码评审、静态分析、动态测试、过程审计等活动。 |
| SCM | 软件配置管理，用于管理软件制品及其变更，核心活动包括配置项确定、配置控制、状态报告和配置审计。 |

### 需求工程

| 名词 | 解释 |
| --- | --- |
| 需求 | 用户为解决问题或达到目标所需要的条件或能力，也包括这种条件或能力的文档化表述。 |
| 需求工程 | 所有需求处理活动的总和，包括需求获取、需求分析、规格说明、需求验证和需求管理。 |
| 问题域 | 需求产生和被解决的现实世界环境，包括领域知识、利益相关人、现有流程和约束条件。 |
| 业务需求 | 高层目标，回答为什么要建设系统，例如销售额提高 20%。 |
| 用户需求 | 用户希望通过系统完成的任务，通常较模糊，需要进一步分析。 |
| 系统级需求 | 面向软件产品的精确规格说明，要求可测试、可追踪、可实现。 |
| 功能需求 | 系统要做什么，描述系统必须提供的功能和行为。 |
| 非功能需求 | 系统要达到什么程度，描述性能、安全、可靠性、可维护性等质量属性和约束。 |
| 用户故事 | 按“作为某角色，我希望某功能，以便某价值”的格式描述需求，并配合验收标准。 |
| INVEST | 好用户故事的准则：独立、可协商、有价值、可估算、小粒度、可测试。 |
| 用例 | 系统与外部对象交互中，为参与者提供有价值服务的一组行为序列。 |
| 场景 | 用例中的单条路径。课件强调：场景是单条路径，用例是所有场景的集合。 |
| Actor | 与系统交互的外部角色，可以是人、外部系统、硬件设备或定时器。 |
| 系统边界 | 划定系统内外范围。Actor 在边界外，用例在边界内。 |
| Include | 包含关系。一个用例必须包含另一个用例的行为。 |
| Extend | 扩展关系。一个用例在特定条件下扩展另一个用例。 |
| 概念类图 | 描述应用领域中重要概念及其关系的模型，也称领域模型。 |
| 顺序图 | 描述一次交互中对象之间消息传递的时间顺序。 |
| OCL | 对象约束语言，用于精确表达 UML 图难以表达的约束。 |
| SRS | 软件规格说明文档，从系统视角以独立、可验证的系统级需求列表描述软件解决方案。 |
| 需求验证 | 检查需求是否正确、完整、一致、可读、可修改。 |
| 需求追踪 | 记录需求与设计、代码、测试之间的对应关系，用于一致性审计和变更影响分析。 |
| 需求冲突 | 需求之间存在矛盾、资源竞争、优先级差异或时序冲突。 |
| SDD | Spec-Driven Development。规格说明成为首要产物，代码由 Spec、Design、Tasks 推导生成。 |

### 体系结构与 HCI

| 名词 | 解释 |
| --- | --- |
| 软件设计 | 创建对象规格说明的活动，回答“怎么组织”，位于需求分析和编程之间。 |
| 分解 | 把大问题拆成子系统、包、类等更小单位。 |
| 抽象 | 隐藏内部细节，只暴露必要接口。 |
| 关注点分离 | 每次只关注系统的一个维度，通过分层和模块化降低复杂度。 |
| 软件体系结构 | 系统的部件、连接件和配置，是最难修改的一类设计决策。 |
| 部件 | 承载系统主要功能的组成单位，例如包、类集合、服务。 |
| 连接件 | 定义部件间交互的抽象表示，例如接口、事件、REST 调用。 |
| 配置 | 部件和连接件之间的组织方式和拓扑结构。 |
| 体系结构风格 | 一组设计决策，规定组件类型、连接方式和拓扑约束。 |
| 分层架构 | 将系统分为展示层、业务逻辑层、数据访问层等，上层依赖下层。 |
| MVC | Model、View、Controller 分离，Model 管理数据和业务逻辑，View 展示，Controller 处理输入。 |
| REST | 以资源为中心设计 URL，用 HTTP 方法表达操作，强调无状态和统一接口。 |
| 微服务 | 将系统拆成可独立部署、独立扩展的小服务，适合大团队和高流量系统，但运维复杂度高。 |
| ASR | 架构重要需求，会影响架构决策的需求，例如并发、安全、可用性、技术约束。 |
| ADR | 架构决策记录，记录背景、决策、理由、被拒绝方案和后果。 |
| 架构气味 | 架构中的结构性问题，例如循环依赖、God Component、层违规调用。 |
| Conway 定律 | 系统架构会受到组织沟通结构的约束。 |
| 可用性 | HCI 的核心目标，包括易学性、效率、易记性、容错性和满意度。 |
| 精神模型 | 用户对任务和系统工作方式的内在理解，界面设计应贴近用户精神模型。 |
| 菲茨定律 | 点击目标越大、越近，完成指向动作越快。用于指导按钮尺寸和位置设计。 |

### 详细设计与面向对象

| 名词 | 解释 |
| --- | --- |
| 详细设计 | 将体系结构决策递归精化到可直接编码的类、方法、数据结构、算法和控制结构。 |
| 职责 | 类要做什么或维护什么，包括操作职责和数据职责。 |
| 协作 | 多个对象通过消息传递共同完成某个行为。 |
| 委托 | 一个对象保留高层职责，把具体执行交给更专门的对象。 |
| GRASP | 通用职责分配原则，用于指导面向对象设计中的职责分配。 |
| Low Coupling | 低耦合。分配职责时尽量减少模块依赖。 |
| High Cohesion | 高内聚。让类保持聚焦，只承担紧密相关的一组职责。 |
| Information Expert | 信息专家原则。把职责分配给拥有完成该职责所需信息的类。 |
| Creator | 创建者原则。由聚合、包含、记录、紧密使用或持有初始化数据的类负责创建对象。 |
| Controller | 控制器原则。为系统事件选择合适的处理对象，避免表现层直接调用领域对象。 |
| 集中式控制 | 少数控制器记录大部分系统行为，决策位置清晰，但控制器容易膨胀。 |
| 委托式控制 | 控制器保留主要决策，把子任务委托给专门对象，是实际系统常用折中方案。 |
| 分散式控制 | 行为广泛分散在对象网络中，控制流难理解，通常应避免。 |
| 模块 | 可独立设计、实现和测试的软件单元。 |
| 耦合 | 模块之间的依赖强度，设计目标是低耦合。 |
| 内聚 | 模块内部元素的关联程度，设计目标是高内聚。 |
| 访问耦合 | 类使用另一个类服务时产生的耦合，包括全局变量、字段访问、参数传递等。 |
| 继承耦合 | 子类依赖父类接口或实现时产生的耦合，比访问耦合更深。 |
| 迪米特法则 | 只与你的直接朋友交谈，避免消息链和间接对象依赖。 |
| 面向接口编程 | 依赖接口而非具体实现，以降低耦合并支持替换和测试。 |
| ISP | 接口隔离原则。调用方不应被迫依赖它不用的方法。 |
| LSP | 里氏替换原则。子类型必须能替换父类型而不改变程序正确性。 |
| 组合优于继承 | 优先通过对象组合复用行为，减少对子类和父类实现细节的依赖。 |
| 信息隐藏 | 每个模块隐藏一个重要设计决策，将变化隔离在模块内部。 |
| 封装 | 用接口隔离实现细节，包括数据、结构、内部对象引用、类型信息和潜在变更。 |
| OCP | 开闭原则。软件实体应对扩展开放，对修改关闭。 |
| DIP | 依赖倒置原则。高层模块和低层模块都应依赖抽象。 |
| SRP | 单一职责原则。一个类只保留一个变化原因。 |
| SOFA | 方法级设计原则：Short、One thing、Few arguments、Abstraction level consistency。 |

### 构造、代码与测试

| 名词 | 解释 |
| --- | --- |
| 软件构造 | 通过编码、验证、单元测试、集成测试、调试等活动生产可工作的软件。 |
| 可读性 | 代码应显而易见地表达意图，便于开发、调试、维护和复用。 |
| 可维护性 | 代码容易修改，复杂度受控，依赖关系清晰。 |
| 契约式设计 | 用前置条件、后置条件、不变式描述方法或类的使用契约。 |
| 防御式编程 | 面对外部输入、环境和依赖对象时主动检查错误，保护内部逻辑。 |
| 调试 | 定位和修复错误的过程，包括重现问题、诊断缺陷、修复缺陷。 |
| 代码评审 | 对代码进行系统检查，发现逻辑、安全、规范和可维护性问题。 |
| 重构 | 不改变代码外部行为的前提下改进内部结构。 |
| 坏味道 | 表明代码需要重构审查的迹象，例如过长方法、大类、过多参数、重复代码。 |
| TDD | 测试驱动开发。先写失败测试，再写实现，最后重构。 |
| Red-Green-Refactor | TDD 三阶段：先让测试失败，再写最小实现让测试通过，再重构。 |
| 单元测试 | 测试单个类、方法或模块是否满足预期。 |
| 集成测试 | 测试多个模块之间的接口和协作是否正确。 |
| 回归测试 | 修改后重新测试已有功能，防止旧功能被破坏。 |

### 设计模式

| 名词 | 解释 |
| --- | --- |
| 设计模式 | 对反复出现的设计结构和协作方式的经验抽象，用于提升灵活性、优雅性和复用性。 |
| 策略模式 | 定义一族算法并分别封装，使它们可以相互替换，让算法变化独立于使用算法的客户。 |
| 抽象工厂模式 | 提供创建一组相关对象的接口，将具体创建逻辑封装在具体工厂中。 |
| 工厂方法模式 | 通过父类定义创建接口，由子类决定实例化哪个类。 |
| 单件模式 | 确保一个类只有一个实例，并提供全局访问点。 |
| 迭代器模式 | 顺序访问聚合对象的元素，而不暴露其内部表示。 |

## 四、复习抓手

复习时可以按下面几条线索串起来：

1. 从现实问题到需求：问题域、利益相关人、需求层次、用例、SRS。
2. 从需求到设计：概念类图、顺序图、ASR、架构风格、ADR。
3. 从设计到代码：职责分配、GRASP、信息隐藏、SOLID、设计模式。
4. 从代码到质量：可读性、契约式设计、测试、调试、代码评审、重构。
5. AI 贯穿全程：生成初稿、辅助建模、辅助审查、辅助测试，但最终判断由工程师负责。
