\subsection{四、继承设计}

\texttt{MyStack extends Vector} 不合理。Stack 只需要压栈、弹栈、大小和空判断，继承 \texttt{Vector} 会暴露大量不属于栈的操作，违反封装和 LSP。改用组合：

\begin{quote}
\footnotesize
\begin{verbatim}
public class MyStack {
    private final Vector elements = new 
Vector();

    public void push(Object element) {
        elements.insertElementAt(element, 
0);
    }

    public Object pop() {
        Object result = 
elements.firstElement();
        elements.removeElementAt(0);
        return result;
    }
}
\end{verbatim}
\end{quote}

\texttt{Employee extends Person} 合理，员工是人，子类没有改变父类语义。若题目关注领域职责，也可让 \texttt{Employee} 扩展工号、职位等属性。

使用表驱动：

\begin{quote}

private static final double[] LIMITS = 
{10000, 20000, 30000, 40000};
private static final double[] RATES = {0.10,
 0.12, 0.15, 0.18, 0.20};

public double tax(double income) {
    if (income <= 0) {
        return 0;
    }
    double tax = 0;
    double previous = 0;
    for (int i = 0; i < LIMITS.length; i++) 
{
        if (income > LIMITS[i]) {
            tax += (LIMITS[i] - previous) * 
RATES[i];
            previous = LIMITS[i];
        } else {
            tax += (income - previous) * 
RATES[i];
            return tax;
        }
    }
    tax += (income - previous) * 
RATES[RATES.length - 1];
    return tax;
}
\end{verbatim}
\end{quote}

\subsection{七、Observer 模式}

结构：

\begin{itemize}
\item \texttt{Student} 是 Subject，保存 \texttt{id}、\texttt{name}、\texttt{birthday}。
\item \texttt{Display1} 和 \texttt{Display2} 是 Observer。
\item \texttt{Display3} 修改 \texttt{Student}。
\item \texttt{Student} 数据变化后通知 \texttt{Display1} 和 \texttt{Display2} 更新。
\end{itemize}

示例：

\begin{quote}
\footnotesize
\begin{verbatim}
public interface Observer {
    void update(Student student);
}

public class Student {
    private String id;
    private String name;
    private String birthday;
    private final List<Observer> observers =
 new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void modify(String id, String 
name, String birthday) {
        this.id = id;
        this.name = name;
        this.birthday = birthday;
        notifyObservers();
    }

    private void notifyObservers() {
        for (Observer observer : observers) 
{
            observer.update(this);
        }
    }
}
\end{verbatim}
\end{quote}

\subsection{九、黑盒与白盒测试}

黑盒测试根据需求规格设计测试，不关注内部代码结构。优点是贴近用户需求，适合功能、边界值和等价类测试；缺点是内部路径覆盖不可见。

白盒测试根据代码结构设计测试。优点是能覆盖语句、分支、条件和路径；缺点是依赖代码实现，对需求遗漏不敏感。

\subsection{六、模块化与信息隐藏}

用户包和优惠券包互相依赖，违反无循环依赖原则，也违反低耦合。改进：

\begin{itemize}
\item 定义 \texttt{CouponIssueService} 作为协调者。
\item 用户包只暴露 \texttt{UserRepository} 或 \texttt{UserService} 接口。
\item 优惠券包只暴露 \texttt{CouponPolicy} 和 \texttt{CouponRepository} 接口。
\end{itemize}

\texttt{issueCoupon} 和 \texttt{addCoupon} 问题：

\begin{itemize}
\item \texttt{issueCoupon} 传入 \texttt{User} 并调用 \texttt{getType()}，存在访问耦合。
\item \texttt{addCoupon} 用 \texttt{type} 控制分支，属于控制耦合。
\item 可接受度低，因为新增用户类型或优惠券类型要修改分支。
\end{itemize}

改进：使用策略或工厂。

\begin{quote}
\footnotesize
\begin{verbatim}
public interface CouponIssuePolicy {
    Coupon issue(User user);
}
\end{verbatim}
\end{quote}

\texttt{user.addCoupon(...)} 多次调用可优化为：

\begin{quote}
\footnotesize
\begin{verbatim}
Coupon coupon = 
couponIssuePolicy.issue(user);
user.receiveCoupon(coupon);
\end{verbatim}
\end{quote}

\subsection{八、\texttt{doPost} 构造分析}

优点：

\begin{itemize}
\item 能读取请求参数并返回结果。
\item 基本流程有成功和失败响应。
\end{itemize}

问题：

\begin{itemize}
\item 参数名 \texttt{new1}、\texttt{new2} 含义弱。
\item \texttt{rsq} 是拼写错误风格，降低可读性。
\item 使用 \texttt{indexOf} 判断密码一致性，逻辑错误；应使用 \texttt{equals}。
\item 条件表达式过长，不可读，不可维护。
\item \texttt{dao.rePassword(new1)} 未传入用户标识。
\item Controller 中混入业务逻辑和数据访问。
\item 没有异常处理和日志。
\item 直接输出字符串 \texttt{"yes"}、\texttt{"no"}，接口语义弱。
\item \texttt{PrintWriter} 手动关闭不适合由容器管理的响应流。
\end{itemize}

改进方向：

\begin{itemize}
\item Controller 调用 \texttt{PasswordService}。
\item 服务中校验旧密码、新密码一致性、新旧密码不同、密码强度。
\item DAO 只负责读取和保存。
\item 返回结构化结果。
\end{itemize}

\subsection{九、HCI}

好的地方：

\begin{itemize}
\item 自助系统降低窗口排队。
\item 余额、充值记录等任务入口明确。
\item 交易结果可即时反馈。
\end{itemize}

问题和建议：

\begin{itemize}
\item 充值按钮和金额输入要靠近，遵循 Fitts 定律。
\item 失败原因要明确，并提供重试入口。

\item 记录列表要支持时间、金额和状态筛选。
\end{itemize}

\subsection{名词解释}

再工程：对已有软件系统进行分析、理解、改造和重新实现，以改善结构、质量、可维护性或适配新平台。再工程通常包括逆向工程、重构、迁移和重新文档化。

\subsection{需求}

判断需求级别：

\begin{itemize}
\item 组织目标和业务价值是业务需求。
\item 用户任务和使用目标是用户需求。
\item 系统输入、处理、输出和约束是系统级需求。
\end{itemize}

判断需求类型：

\begin{itemize}
\item 系统做什么：功能需求。
\item 性能、安全、可用性等质量属性：非功能需求。
\item 数据字段、取值范围、格式：数据需求。
\item 和外部系统通信：对外接口需求。
\item 技术栈、法规、平台限制：约束。
\end{itemize}

从用户级需求到系统需求：

\begin{enumerate}
\item 访谈利益相关者。
\item 写用户故事和用例。
\item 梳理基本流程和扩展流程。
\item 提取系统输入、处理和输出。
\item 补充数据、接口和非功能约束。
\item 写成可验证的 SRS 条目。
\end{enumerate}

\subsection{详细设计}

Controller-Service-Repository 顺序图：

\begin{quote}
\footnotesize
\begin{verbatim}
User -> Controller: request
Controller -> Service: method(command)
Service -> Repository: query/save
Repository --> Service: entity
Service --> Controller: result
Controller --> User: response
\end{verbatim}
\end{quote}

控制策略：

\begin{itemize}
\item 集中式：流程集中，控制器臃肿。
\item 分散式：流程分布广，追踪困难。
\item 委托式：控制器保留主流程，把子任务交给专业对象。业务系统优先采用委托式。
\end{itemize}

\subsection{代码好坏}

坏代码特征：

\begin{itemize}
\item 方法过长。
\item 分支复杂。
\item 命名无意义。
\item 重复代码。
\item 直接访问内部结构。
\item 多个职责混在一个类或方法。

好代码特征：

\begin{itemize}
\item 命名清楚。
\item 职责单一。
\item 依赖接口。
\item 分支被策略或多态替代。
\item 测试覆盖边界和异常。
\end{itemize}

\begin{verbatim}

public class TeacherConflictCheckStrategy 
implements ConflictCheckStrategy {

check(ScheduleContext context) {
        return ConflictResult.pass();
    }
}

public class ClassroomConflictCheckStrategy 
implements ConflictCheckStrategy {
    public ConflictResult 
check(ScheduleContext context) {
        return ConflictResult.pass();
    }
}

public class 
StudentCourseConflictCheckStrategy 
implements ConflictCheckStrategy {
    public ConflictResult 
check(ScheduleContext context) {
        return ConflictResult.pass();
    }
}

public class ConflictCheckContext {
    private final 
List<ConflictCheckStrategy> strategies;

    public ConflictCheckContext(List<Conflic
tCheckStrategy> strategies) {
        this.strategies = strategies;
    }

    public List<ConflictResult> 
checkAll(ScheduleContext context) {

                .map(strategy ->
