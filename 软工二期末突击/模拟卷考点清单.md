## 一、名词解释 / 简答

模块：软件工程基础、体系结构、软件构造、人机交互、软件文档。

固定结构：3 个小问；`软件工程` 在 8 套中均为第 1 小问，4 分；其余两个小问各 3 分。

具体考点：

- `软件工程`：系统化、规范化、可量化；开发、运行、维护；工程化方法。
- `再工程与逆向工程`：二者定义、工作目标、区别。
- `软件体系结构`：高层组织结构；部件、连接件、配置；重要设计决策和质量属性。
- `可用性`：易学性、效率、易记性、容错性、满意度。
- `重构`：不改变外部可观察行为，改善内部结构。
- `测试驱动开发（TDD）`：先写测试，再写实现，再重构。
- `结对编程`：两人共同完成同一任务，驾驶员与观察员协作。
- `用户文档与系统文档`：面向使用者的操作说明与面向开发维护者的系统说明。

## 二、需求获取与需求分类

模块：需求工程。

固定结构：

- 识别主要参与者，写出 3 个相关用例，并分别用一句话说明主要流程。
- 分别写出一个业务需求、用户需求、系统级需求。
- 从数据需求、质量需求、对外接口需求中各写一项，并说明分类依据。

具体考点：

- 参与者识别：业务用户、管理人员、外部系统、平台服务。
- 用例识别：用例名、参与者、系统交互主流程。
- 需求层次：业务需求写组织目标，用户需求写用户任务，系统级需求写系统必须提供的行为或约束。
- 需求类型：数据需求写保存和维护的数据；质量需求写性能、可靠性、可用性等质量属性；对外接口需求写外部 API、协议、平台或系统对接。
- 分类依据：每一项都要写“结论 + 场景依据”。

## 五、详细设计

模块：详细设计、职责分配、对象协作、控制风格。

固定结构：

- 根据系统顺序图细化指定用例。
- 分配 `Controller`、`Service`、`Repository`、领域对象和外部接口的职责。
- 画出包含对象消息调用的详细顺序图。
- 判断本场景适合集中式、分散式还是委托式控制，并说明理由。

具体考点：

- `Controller`：接收请求、参数转换、返回结果。
- `Service`：组织用例流程、协调事务、调用领域对象和仓储接口。
- `Repository`：持久化与查询，隐藏数据库细节。
- 领域对象：保存业务状态，封装业务规则。
- 外部接口：支付、消息、供应商、文件、HTTP 平台等外部系统访问。
- 详细顺序图：对象生命线、同步调用、返回、外部系统交互、异常分支。
- 控制风格：集中式控制强调由控制对象统一调度；分散式控制强调职责分散到领域对象；委托式控制强调控制对象协调并把业务规则委托给领域对象或策略对象。

8 套细化用例与第四题一致：校园卡充值、预约图书、预约门诊号源、提交选课、生成采购补货单、预约实验设备、提交外卖订单、预订客房。

## 六、代码结构分析与设计原则

模块：模块化、设计原则、耦合内聚、信息隐藏、职责拆分。

固定结构：

- 指出至少 3 个违反的设计原则或模块化问题，并结合代码说明。
- 从耦合、内聚和信息隐藏角度分析危害。
- 给出职责拆分类图或代码结构，说明依赖方向。

具体考点：

- `SRP`：一个类混合业务规则、数据访问、外部通知、界面反馈、日志等多个职责。
- `DIP`：高层业务类直接依赖具体数据库、DAO、SDK、文件、HTTP 客户端。
- 信息隐藏：直接暴露字段、集合、SQL、表结构、状态字符串、文件格式、外部平台细节。
- 封装：领域对象应通过方法保护状态变化，不应让外部直接修改内部字段或集合。
- 耦合：具体实现变化会扩散到业务代码，测试时难以替换依赖。
- 内聚：类职责过多，修改原因过多，维护定位困难。
- 改进结构：`Controller -> Service interface -> Service implementation -> Repository interface / Domain / External Gateway`。

## 七、策略模式

模块：设计模式、封装变化、OCP、DIP、SRP。

固定结构：

- 说明为什么适合使用策略模式。
- 画出 `Strategy`、三个 `ConcreteStrategy` 和 `Context` 的类图。
- 写策略接口、一个具体策略和 `Context` 的代码骨架。
- 说明优缺点，并写出 `OCP`、`DIP`、`SRP` 在该设计中的体现。

具体考点：

- 识别变化点：不同身份、类型、规则、场景采用不同算法。
- 抽象 `Strategy` 接口，定义统一算法入口。
- 每一种规则写一个 `ConcreteStrategy`。
- `Context` 持有策略接口，不直接依赖具体策略类。
- `OCP`：新增规则时新增具体策略，不修改主流程。
- `DIP`：上下文依赖策略接口。
- `SRP`：每个策略只负责一种算法。
- 优点：消除复杂条件、便于扩展、便于单独测试。
- 缺点：类数量增加，配置层或调用方需要选择策略。

## 八、软件构造与代码改进

模块：软件构造、代码可读性、可维护性、可靠性、控制结构。

固定结构：

- 写出代码的优点和至少 3 个缺点。
- 说明采用哪些改进方法：提取方法、命名条件、表驱动、减少嵌套、防御式编程或契约式设计。
- 写出改进后的代码或伪代码。

具体考点：

- 可读性：变量名、方法名、条件表达式、复杂布尔表达式。

- 可靠性：空值、非法输入、异常吞掉、静默返回、哨兵值、后置条件缺失。
- 控制结构：嵌套过深、冗长 `if-else`、重复循环、过长返回表达式。
- 改进方法：提取方法、命名条件、表驱动、提前返回、减少嵌套、防御式检查、契约式设计。

## 九、软件测试：文字测试用例

模块：软件测试、黑盒测试、功能测试、测试用例设计。

固定结构：

- 选择等价类划分、边界值、决策表或状态转换中的适当方法，并说明选择理由。
- 用文字表格设计不少于 6 个测试用例。
- 每项写输入/前置条件、操作、预期输出和覆盖点。

具体考点：

- 等价类划分：合法输入类、非法输入类、业务状态类。
- 边界值：最小值、最大值、边界内、边界外、时间边界。
- 决策表：多个业务条件组合决定同一输出。
- 状态转换：订单、预约、支付、取消、过期等状态变化。
- 异常路径：支付失败、库存不足、号源不足、房量为 0、超时、冲突。
- 后置条件：失败时余额、记录、号源、库存、订单、通知等不得产生错误变化。

## 十、人机交互界面分析

模块：人机交互、可用性、界面原则、错误预防与反馈。

固定结构：

- 写出至少 2 个优点和 3 个不足。
- 每一点都要写清“界面现象 -> 原则 -> 对用户的影响”。
- 针对不足给出可执行的改进建议。

具体考点：

- 导航：页面标题、顶部导航、侧边栏、当前位置。
- 反馈：状态、进度、处理结果、失败原因、恢复入口。
- 精神模型：术语、任务路径、业务规则是否符合用户经验。
- 识别而非回忆：金额、日期、数量、对象、状态、规则要直接展示。
- 错误预防：危险操作隔离、二次确认、禁用不可用按钮、提交前说明后果。
- 差异性：重要状态、主次按钮、风险提示要有视觉区分。
- 隐私与敏感信息：卡号、地址、支付信息等需要适当遮挡或确认。

## 复习使用顺序

1. 先背第 1 题名词解释清单，尤其是 `软件工程` 的固定关键词。
2. 第 2 至 5 题按同一业务场景连做：需求识别 -> 概念类图 -> 分层包图和接口 -> 详细顺序图。
3. 第 6 和第 8 题统一使用“点名问题 -> 代码证据 -> 危害 -> 改法”的答题结构。
4. 第 7 题固定背策略模式类图和代码骨架，再把业务算法名替换为题干变化点。
5. 第 9 题先选测试方法，再写不少于 6 条覆盖有效、无效、边界、异常、状态变化的测试用例。
6. 第 10 题每点必须写完整链条：“界面现象 -> 原则 -> 用户影响 -> 改进建议”。
