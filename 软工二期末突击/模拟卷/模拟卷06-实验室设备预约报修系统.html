软件工程。

软件工程是将系统化、规范化、可量化的方法应用于软件开发、运行和维护的过程，即将工程化方法应用于软件；同时也研究这些方法本身。

评分：系统化、规范化、可量化 2 分；开发、运行、维护 1 分；工程化方法 1 分。

说明增量迭代模型与演化模型的区别。

增量迭代模型强调按计划把功能分批交付，每轮完成一部分可运行系统；演化模型先提供初始版本，再根据用户反馈、环境变化和新需求持续改变系统。前者侧重有计划的分批交付，后者侧重反馈驱动的持续演化。

评分：两种模型各 1 分；准确指出计划驱动与反馈驱动的差别 1 分。

可用性。

可用性是衡量特定用户在特定环境中使用系统完成任务时是否容易、有效并感到满意的质量属性，常从易学性、效率、易记性、容错性和满意度衡量。

评分：定义 1 分；易学性、效率、易记性、容错性、满意度中写出三项得 2 分。

职责分配

控制风格

逐问完整写法

  1. 职责分配：Controller 接收请求并调用 Service；Service 控制用例主流程和事务；Repository 查询和保存领域对象；领域对象或 Policy 执行业务校验和状态变化；外部 Gateway 封装支付、通知、身份核验或第三方系统。
  2. 详细顺序图：参与者 → Controller：提交 command；Controller → Service：调用业务方法；Service → Repository：查询领域对象；Service → Domain/Policy：校验业务规则；Service → Gateway：调用外部系统；Service → Repository：保存状态和记录；Service → Controller：返回 result；Controller → 参与者：显示结果与编号。
  3. 控制风格：本场景适合委托式控制。Service 保留主流程，把持久化、外部调用和领域规则分别委托给专门对象，避免 Controller 或单个类承担全部职责。

画顺序图时，核心调用用实线，关键返回结果用虚线；保存类的 void 返回不必逐一画出。

第 1 问：违反的原则或模块化问题

  1. 违反 DIP：业务代码直接依赖具体数据库、DAO、SDK、文件或外部客户端，不能稳定依赖接口。

第 2 问：耦合、内聚和信息隐藏危害

  • 耦合：底层实现变化会影响业务类，单元测试也难以替换依赖。
  • 内聚：一个类混合多种职责，功能越改越臃肿，维护时难以定位修改点。
  • 信息隐藏：外部对象能制造非法状态，领域规则无法集中保护。

public interface ApprovalStrategy {
    boolean approve(Reservation request);
}

public final class AutomaticApprovalStrategy implements ApprovalStrategy {
    @Override
    public boolean approve(Reservation request) {
        // 本策略只实现一种规则

  • OCP：新增规则时增加具体策略，不修改 Context。
  • DIP：Context 依赖策略接口。
  • SRP：每个策略只负责一种算法。
  • 优点是消除复杂条件并便于独立测试；缺点是类数量增加，配置层必须选择策略。

第 4 问：原则和优缺点

  • OCP：新增规则时增加具体策略，不修改 Context 主流程。
  • DIP：Context 依赖策略接口，不依赖具体策略类。
  • SRP：每个具体策略只负责一种算法。
  • 优点：消除复杂条件分支，便于独立测试和扩展。
  • 缺点：类数量增加，需要在配置层、工厂或运行时选择正确策略。

第 3 问：代码骨架完整写法

public interface ApprovalStrategy {
    boolean approve(Reservation request);
}

public final class AutomaticApprovalStrategy implements ApprovalStrategy {
    @Override
    public boolean approve(Reservation request) {
        return false;
    }
}

public final class StrategyContext {
    private final ApprovalStrategy strategy;

    public StrategyContext(ApprovalStrategy strategy) {
        this.strategy = strategy;
    }

    public boolean execute(Reservation request) {
        return strategy.approve(request);
    }
}

第 1 问：优点和缺点

优点：代码试图先检查用户和设备状态，再保存预约，主流程目标比较明确。

  • 缺点 1：空值风险明显。user.getId()、equipment.status 在没有判空时直接访问，容易产生空指针异常。
  • 缺点 2：吞掉异常。catch (Exception e) { } 完全忽略错误，调用者只能得到 null，无法知道失败原因。
  • 缺点 3：直接访问内部字段。equipment.status.equals("OK") 暴露设备状态表示方式，应由设备对象提供业务方法。
  • 缺点 4：业务校验不完整。代码没有体现时段合法性、设备在该时段是否冲突等预约规则。

第 2 问：改进方法

  • 防御式编程 / 契约式设计：对 user、equipment、slot 使用 Objects.requireNonNull 明确前置条件。
  • 命名条件：用 equipment.isAvailable() 表达设备可预约状态，替代字符串比较。
  • 提取方法或策略：用 conflictPolicy.ensureAvailable 封装时段冲突检查。
  • 可靠性改进：不吞掉异常；不可预约时抛出明确异常，让调用者能处理失败原因。

第 3 问：改进代码

Reservation reserve(User user, Equipment equipment, TimeSlot slot) {
    Objects.requireNonNull(user, "user");
    Objects.requireNonNull(equipment, "equipment");
    Objects.requireNonNull(slot, "slot");

    if (user.getId() == null || user.getId().isBlank()) {
        throw new IllegalArgumentException("user");
    }
    if (!equipment.isAvailable()) {
        throw new EquipmentUnavailableException();
    }

    conflictPolicy.ensureAvailable(equipment.id(), slot);
    return repository.save(Reservation.create(user, equipment, slot));
}

改进后，非法输入、设备不可用和时段冲突都有明确处理；方法不再返回含义不清的 null，也不再吞掉异常。

卷面粒度：每一点按“界面现象 → 原则 → 用户影响 → 改进建议”写。优点至少 2 个，不足至少 3 个。

第 1 问：优点和不足

  1. 页面显示“可用”，但所选时长超过 4 小时，状态反馈与规则不一致。
  2. “确认”未说明确认预约，动作命名不具体。
  3. 取消预约是另一业务动作，不应在新建预约页与主按钮并列。
  4. 危险设备审核规则有提示，是错误预防方面的优点。
  5. 日期未写年份和星期，可能导致识别错误。
  6. 应实时显示冲突、时长和审核状态，并在提交后给出预约编号。

第 2 问：按原则展开的写法

  • 导航和标题是优点：顶部导航、侧边栏和页面标题能说明当前位置，符合导航可见性原则，用户能确认自己正在处理的业务。
  • 关键信息展示是优点：业务对象、金额、日期、状态等集中展示，符合识别而非回忆原则，用户能在提交前核对信息。
  • 动作名称不明确是缺点：“确定、提交、确认、订、选上、执行”等文案没有说明后果，违反动作明确和错误预防原则，用户容易误操作。
  • 规则或状态反馈不足是缺点：范围、截止时间、排队、审核、取消规则或处理中状态不完整，违反反馈原则，用户无法判断下一步和后果。
  • 危险操作靠近主操作是缺点：取消、删除、清除等操作与主按钮距离近或样式相近，违反错误预防原则，用户容易误点。

第 3 问：可执行改进

  • 把主按钮改成带业务后果的文案，例如“确认充值并支付”“确认预约此书”“确认提交选课”。
  • 在输入项旁显示范围、单位、截止时间、排队顺序、审核规则或取消费用。
  • 处理中禁用重复提交，并显示当前阶段和失败后的恢复入口。
  • 删除、取消、清除等危险操作弱化显示、拉开距离，并增加二次确认。

只写“界面不友好”不得分；必须对应到具体界面现象和人机交互原则。
