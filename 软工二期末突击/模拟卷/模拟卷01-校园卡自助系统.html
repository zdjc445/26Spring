软件工程。

软件工程是将系统化、规范化、可量化的方法应用于软件开发、运行和维护的过程，即将工程化方法应用于软件；同时也研究这些方法本身。

评分：系统化、规范化、可量化 2 分；开发、运行、维护 1 分；工程化方法 1 分。

解释再工程与逆向工程，并说明二者的区别。

逆向工程从已有系统出发，分析并恢复其部件、关系、需求或设计，重点是理解和抽象恢复；再工程在理解旧系统的基础上进一步改造、重构、迁移或重新实现，以改善质量、可维护性或平台适应性。逆向工程偏重理解，再工程包含改造。

评分：逆向工程 1 分；再工程 1 分；区别 1 分。

说明增量迭代模型与演化模型的区别。

增量迭代模型强调按计划把功能分批交付，每轮完成一部分可运行系统；演化模型先提供初始版本，再根据用户反馈、环境变化和新需求持续改变系统。前者侧重有计划的分批交付，后者侧重反馈驱动的持续演化。

评分：两种模型各 1 分；准确指出计划驱动与反馈驱动的差别 1 分。

参与者与用例

主要参与者：学生，以及场景中的管理员或外部系统。核心用例：查询余额、提交充值、查询充值记录。

需求层次

  • 业务需求：降低人工充值窗口压力，使大部分充值业务在线完成。
  • 用户需求：学生能够随时提交充值并查看结果与历史记录。
  • 系统级需求：系统在收到支付成功通知后更新校园卡余额并保存不可重复的充值记录。

需求类型

  • 数据需求：保存卡号、充值订单号、金额、渠道、状态和时间。
  • 质量需求：正常情况下充值结果应在 3 秒内反馈。
  • 对外接口需求：系统通过 HTTPS/JSON 调用支付平台，并向校园卡中心发送余额更新请求。

public class RechargeManager {

        System.out.println("recharge=" + amount);
    }
}

问题定位

  • 业务类直接依赖 MysqlCardRepository 和 SmsClient，违反 DIP。
  • 一个类同时承担业务、数据访问、通知和日志职责，违反 SRP，内聚性低。

public interface PointStrategy {
    int calculate(RechargeOrder order);
}

public final class NormalPointStrategy implements PointStrategy {
    @Override
    public int calculate(RechargeOrder order) {
        // 本策略只实现一种规则
        return 0;
    }
}

public final class StrategyContext {
    private final PointStrategy strategy;

    public StrategyContext(PointStrategy strategy) {
        this.strategy = strategy;
    }
}
  • OCP：新增规则时增加具体策略，不修改 Context。
  • DIP：Context 依赖策略接口。
  • SRP：每个策略只负责一种算法。
  • 优点是消除复杂条件并便于独立测试；缺点是类数量增加，配置层必须选择策略。
