软件工程。

软件工程是将系统化、规范化、可量化的方法应用于软件开发、运行和维护的过程，即将工程化方法应用于软件；同时也研究这些方法本身。

评分：系统化、规范化、可量化 2 分；开发、运行、维护 1 分；工程化方法 1 分。

重构。

重构是在不改变软件外部可观察行为的前提下，调整内部结构，以提高可读性、可维护性和可扩展性的过程。

评分：不改变外部行为 1 分；调整内部结构 1 分；质量目标 1 分。

测试驱动开发（TDD）。

TDD 是先写一个失败的自动化测试，再编写刚好使测试通过的代码，最后在测试保护下重构，并不断重复红、绿、重构循环。

评分：先写测试、使测试通过、重构各 1 分。

第 1 问：违反的原则或模块化问题

  1. 违反 DIP：业务代码直接依赖具体数据库、DAO、SDK、文件或外部客户端，不能稳定依赖接口。
  2. 违反 SRP：同一个类同时处理业务规则、数据访问、通知、日志或界面反馈，修改原因过多。
  3. 破坏信息隐藏：直接访问字段、集合、状态字符串、SQL 行或表结构，绕过领域对象封装。
  4. 可靠性不足：缺少输入校验、事务边界、异常处理或失败结果表达。

第 2 问：耦合、内聚和信息隐藏危害

  • 耦合：底层实现变化会影响业务类，单元测试也难以替换依赖。
  • 内聚：一个类混合多种职责，功能越改越臃肿，维护时难以定位修改点。
  • 信息隐藏：外部对象能制造非法状态，领域规则无法集中保护。

第 3 问：职责拆分结构

Controller -> Service interface
Service implementation -> Repository interface
Service implementation -> Domain / Policy
Service implementation -> External Gateway interface
Repository / Gateway implementation -> Database / SDK / File / HTTP
  • Controller 只负责接收请求和返回结果。
  • Service 负责用例流程和事务。
  • Repository 负责持久化，隐藏 SQL、文件或 ORM。
  • 领域对象封装状态变化，例如 credit、reserve、enroll、book 等业务方法。
  • 外部系统通过 Gateway 或 Notifier 接口访问。

  • DIP：Context 依赖策略接口，不依赖具体策略类。
  • SRP：每个具体策略只负责一种算法。
  • 优点：消除复杂条件分支，便于独立测试和扩展。
  • 缺点：类数量增加，需要在配置层、工厂或运行时选择正确策略。

卷面粒度：第 1 问按“优点 + 至少 3 个缺点”写；第 2 问点名改进方法并说明落实位置；第 3 问给出可执行的改进代码或伪代码。

第 1 问：优点和缺点

优点：代码直接表达了时间段重叠的核心判断：同一天且两个时间段相互交叉。

  • 缺点 1：重复判断。a.day == x.day && a.start < x.end && x.start < a.end 在两个循环中重复出现，修改重叠规则时容易漏改。
  • 缺点 2：直接访问字段。a.day、a.start、a.end、a.room 暴露了 Course 的内部结构，缺少领域方法。
  • 缺点 3：职责混杂。学生课表时间冲突和教室占用冲突放在同一个 conflict 方法中，方法含义不够单一。
  • 缺点 4：命名过短。list、x、a 无法表达“已选课程”“目标课程”等业务含义。

第 2 问：改进方法

  • 提取方法：把时间重叠判断提取为 overlaps，避免重复代码。
  • 命名条件：用 hasStudentConflict 和 hasRoomConflict 分别命名两类冲突。
  • 信息隐藏：通过 Course.slot()、course.sameRoomAs(target) 访问业务含义，而不是直接读字段。
  • 减少重复：两类冲突都复用 overlaps。

第 3 问：改进代码

boolean overlaps(TimeSlot a, TimeSlot b) {
    return a.day().equals(b.day())
            && a.start().isBefore(b.end())
            && b.start().isBefore(a.end());
}

boolean hasStudentConflict(List<Course> selected, Course target) {
    return selected.stream()
            .anyMatch(course -> overlaps(course.slot(), target.slot()));
}

boolean hasRoomConflict(List<Course> courses, Course target) {
    return courses.stream()
            .filter(course -> course.sameRoomAs(target))
            .anyMatch(course -> overlaps(course.slot(), target.slot()));
}

boolean conflict(List<Course> selected, List<Course> courses, Course target) {
    return hasStudentConflict(selected, target)
            || hasRoomConflict(courses, target);
}

改进后，时间重叠规则只有一处；学生冲突和教室冲突分开表达，方法职责更清楚。

参考答案与评分点

卷面粒度：每一点按“界面现象 → 原则 → 用户影响 → 改进建议”写。优点至少 2 个，不足至少 3 个。

第 1 问：优点和不足

  1. “选上”口语化且结果未发生前带有承诺，应改为“提交选课”。
  2. 冲突状态显示“未检测”，但主按钮仍可直接点击，错误预防不足。
  3. 余量写成 1/60，未说明前者是剩余还是已选。
  4. 课程、时间、容量集中展示，减少用户记忆负担。
  5. 应在提交后给出明确成功/失败反馈和失败原因。
  6. 返回按钮清晰，但应保留检索条件，支持操作恢复。

第 2 问：按原则展开的写法

  • 导航和标题是优点：顶部导航、侧边栏和页面标题能说明当前位置，符合导航可见性原则，用户能确认自己正在处理的业务。
  • 关键信息展示是优点：业务对象、金额、日期、状态等集中展示，符合识别而非回忆原则，用户能在提交前核对信息。
  • 动作名称不明确是缺点：“确定、提交、确认、订、选上、执行”等文案没有说明后果，违反动作明确和错误预防原则，用户容易误操作。
  • 规则或状态反馈不足是缺点：范围、截止时间、排队、审核、取消规则或处理中状态不完整，违反反馈原则，用户无法判断下一步和后果。
  • 危险操作靠近主操作是缺点：取消、删除、清除等操作与主按钮距离近或样式相近，违反错误预防原则，用户容易误点。

第 3 问：可执行改进

  • 把主按钮改成带业务后果的文案，例如“确认充值并支付”“确认预约此书”“确认提交选课”。
  • 在输入项旁显示范围、单位、截止时间、排队顺序、审核规则或取消费用。
  • 处理中禁用重复提交，并显示当前阶段和失败后的恢复入口。
  • 删除、取消、清除等危险操作弱化显示、拉开距离，并增加二次确认。

只写“界面不友好”不得分；必须对应到具体界面现象和人机交互原则。
