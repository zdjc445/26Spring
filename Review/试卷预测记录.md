## 第一大题：名词解释

### 第 1 小问：软件工程

状态：已确定。

PPT 原话来源：`PPT/01-01-软件工程基础.pdf` 第 30 页。

原话：

> 软件工程是将系统化的、规范化的、可量化的方法
> 应用于软件的开发、运行和维护的过程；
> 即将工程化的方法应用于软件。

考试写法：

软件工程是将系统化、规范化、可量化的方法应用于软件开发、运行和维护的过程，即将工程化方法应用于软件。它也研究这些方法本身。

得分关键词：

- 系统化
- 规范化
- 可量化
- 开发
- 运行
- 维护
- 工程化方法

### 第 2、3 小问：按优先级准备

当前优先级：

1. 再工程/逆向工程。
2. 增量迭代模型和演化模型的区别。
3. 从 1950s 到 2000s 软件工程发展的特点。
4. 体系结构的概念。
5. 可用性。
6. 耦合与内聚。
7. 重构。
8. 测试驱动开发 TDD。
9. 结对编程。
10. 用户文档、系统文档。

重点写法：

- 再工程：对已有软件系统进行分析、理解、改造和重新实现，以改善结构、质量、可维护性或适配新平台。
- 逆向工程：从已有系统出发，分析并恢复系统的部件、关系、需求或设计，重点是理解和抽象恢复。
- 增量迭代模型和演化模型的区别：增量迭代模型强调有计划地分批交付功能，每轮迭代完成一部分可运行系统；演化模型强调先交付初始版本，再根据用户反馈、环境变化和新需求持续调整、扩展和完善系统。
- 体系结构的概念：软件体系结构是软件系统的高层组织结构，由部件、连接件和配置组成。
- 可用性：可用性是衡量用户使用系统完成任务时是否容易、有效和满意的质量属性，包括易学性、效率、易记性、容错性和满意度。

依据：

- `Exam/2025.pdf` 第一大题名词解释区域出现“再工程”“增量迭代模型和演化模型的差别”。
- `Exam/2022.pdf` 第一大题考“迭代增量模型和演化模型的差异及优缺点”。
- `Review/复习提纲.pdf` 中明确列出体系结构概念、可用性、耦合与内聚、重构、TDD、结对编程、逆向工程、再工程等名词或概念。

## 第四大题：体系结构设计

当前准备方向：分层包图/物理包图 + 层间接口。

核心判断：第四题不按“解释体系结构概念”准备，而按“给场景 -> 分层包图/物理包图 -> 层间接口”准备。接口定义是本题最高优先级。

复习提纲体系结构例题原型：

1. 薪酬管理系统采用 Web 框架实现，按分层体系结构风格设计，画具体物理包图。要求体现系统所有功能模块、跨网络、浏览器端 HTML/CSS/JS、服务器端逻辑层和数据层、HTTP 通信、REST 风格 API 接口。（4 分）
2. 设计“社会保险录入”页面对应的展示层与逻辑层交互接口，以及相关逻辑层与数据层交互接口。要求写接口声明代码，不写实现，并写出每个接口所属包名，注意接口在包中的分布。（6 分）

题目形式：

1. 给一个业务系统场景。
2. 按分层体系结构设计包结构或物理包图。
3. 图中体现客户端、服务器端、展示层、逻辑层、数据层。
4. Web 系统体现浏览器端 HTML、CSS、JS，以及 HTTP / REST API 通信。
5. 服务器端按 `controller / service / repository(dao) / entity` 或展示层/逻辑层/数据层组织。
6. 针对指定业务用例，写展示层与逻辑层之间的接口。
7. 写逻辑层与数据层之间的接口。
8. 接口只写声明，不写实现；写清包名、接口名、方法名、参数和返回值。

分值侧重：

- 包图/包结构：约 4 分。
- 层间接口、包名、依赖方向：约 5-6 分。
- 三层职责、风格理由、集成策略：约 1 分。

三层职责模板：

分层架构将系统划分为展示层、业务逻辑层和数据访问层。展示层负责接收用户请求、展示结果并调用业务接口；业务逻辑层负责实现业务规则、协调业务流程和事务；数据访问层负责数据持久化和数据库访问。层间通过接口交互，依赖方向为展示层依赖业务逻辑层、业务逻辑层依赖数据访问层，上层不直接依赖下层实现类，从而降低耦合、隐藏实现并提高可测试性和可维护性。

2025 风格变体：

1. 简述 Spring Boot 中三层的作用和职责。
2. 写 `Service` 接口声明。
3. 写 `Repository` 方法声明。
4. 写 `Controller` 调用 `Service` 的代码片段，并体现依赖注入。

## 第六大题：代码结构分析与设计原则

当前准备方向：给代码、类图或包关系，问违反了什么原则，如何改进；重点结合职责拆分类。

覆盖内容：

- 耦合与内聚。
- 信息隐藏和封装。
- 模块化原则。
- OCP。
- DIP。
- 结合职责拆分类，重点对应 SRP 单一职责原则。

复习提纲内容：

- 第十三章：名词解释耦合与内聚；对例子说明耦合程度与内聚并给出理由；信息隐藏的基本思想；两种常见的信息隐藏决策；对例子说明信息隐藏程度好坏。
- 第十四章：模块化原则，包括 DRY、Programming to Interface、Law of Demeter、ISP、LSP、组合优于继承、SRP 等；对给定示例发现违反的原则并修正。
- 第十五章：信息隐藏的含义、封装、OCP、DIP。

题目形式：

1. 给一段代码或类图。
2. 判断代码违反了什么设计原则。
3. 从耦合、内聚、信息隐藏角度说明坏处。
4. 结合职责拆分类。
5. 给出修改方案，必要时画修改后的类图、包图或写修改后的代码片段。

重点原则对应：

- SRP：一个类承担多个职责，存在多个变化原因，应按职责拆分类。
- 信息隐藏/封装：暴露了内部数据结构、算法、文件格式、数据库访问或实现细节。
- OCP：新增需求或新类型时必须修改旧代码，应通过抽象、接口、策略或多态扩展。
- DIP：高层业务直接依赖低层实现，应改为高层和低层都依赖抽象接口。
- Law of Demeter：对象过度访问其他对象内部结构，应减少链式访问并封装委托。
- DRY：重复逻辑散落在多个地方，应抽取公共方法或类。
- LSP：子类不能替换父类，应重新设计继承关系或使用组合。

- `Exam/2012.pdf`：给 `SalesView / SalesLogic / SalesData` 分层代码，问各自隐藏的 `Secret`，是否违反信息隐藏原则并修正；另问 `SalesLogic` 和 `SalesData` 违反哪条面向对象设计原则，解释并修正。
- `Exam/2013A.pdf`：给应用描述代码，问是否违反设计原则，是否能用设计模式重构；给 `validate_request`、`valid_month`、`valid` 代码，问是哪种耦合并修改；给继承设计，问是否违反原则并修改。
- `Exam/2013B.pdf`：给 `getSubtotal` 代码，问内聚性和设计原则，并画修改后的顺序图；给 `averageGradeforTop50` 和 `ArrayList<Student>`，问是哪种耦合并修改。
- `Exam/2016.pdf` 第 6 大题：简述如何消除印记耦合。
- `Exam/2020.pdf` 第 6 题：给 `validate_request` 相关代码，问方法之间是哪种耦合，如何修改。
- `Exam/2022.pdf` 第 6 题：模块化与信息隐藏，问包相互依赖违反什么包原则、如何修改并画图；问代码中是哪种耦合，是否可接受，如何修改。

答题结构：

1. 先点名原则：例如 SRP、OCP、DIP、信息隐藏、Law of Demeter。
2. 再指出代码现象：哪个类做了多个职责，哪个模块依赖了具体实现，哪个实现细节被暴露。
3. 再说明危害：高耦合、低内聚、修改扩散、难测试、难扩展。
4. 最后给改法：拆类、抽接口、封装变化点、减少参数暴露、把重复代码抽取出来、用组合替代不合理继承。

## 第七大题：策略模式

状态：已确定会考策略模式。

当前准备方向：给变化点场景，使用策略模式进行设计，写接口、具体策略类和 Context 类，并说明优缺点和设计原则。

常见场景：

- 多种积分计算规则。
- 多种支付方式。
- 多种优惠券规则。
- 多种订货规则。
- 多种冲突检测规则。
- 多种算法可以互换。

题目形式：

1. 给定一个规则会变化的业务场景。
2. 要求判断使用什么设计模式。
3. 写策略接口。
4. 写多个具体策略实现。
5. 写 `Context` 类。
6. 说明使用该模式的优点、缺点和相关设计原则。

2025 风格准备：

- 情境：课程冲突检测。
- 策略接口：冲突检测策略接口。
- 具体策略：教师冲突检测、教室冲突检测、学生选课冲突检测。
- `Context`：持有策略接口，根据需要调用具体检测策略。

答题结构：

1. 抽象出 `Strategy` 接口，定义统一算法入口。
2. 每一种规则写一个 `ConcreteStrategy`。
3. `Context` 持有 `Strategy` 接口，而不是依赖具体策略类。
4. 客户端选择具体策略并注入 `Context`。
5. 说明新增规则时只新增具体策略类，不修改已有上下文逻辑。

必须写到的设计原则：

- OCP：新增策略时扩展新类，不修改已有代码。
- DIP：`Context` 依赖策略接口，不依赖具体策略实现。
- SRP：每个具体策略只负责一种规则或算法。
- 低耦合：业务上下文和具体算法分离。
- 封装变化：把变化的算法或规则封装到独立策略类中。

代码骨架：

```java
public interface ConflictStrategy {
    boolean hasConflict(CourseArrange arrange);
}

public class TeacherConflictStrategy implements ConflictStrategy {
    public boolean hasConflict(CourseArrange arrange) {
        // 判断教师时间冲突
        return false;
    }
}

public class ClassroomConflictStrategy implements ConflictStrategy {
    public boolean hasConflict(CourseArrange arrange) {
        // 判断教室时间冲突
        return false;
    }
}

public class StudentConflictStrategy implements ConflictStrategy {
    public boolean hasConflict(CourseArrange arrange) {
        // 判断学生选课冲突
        return false;
    }
}

public class ConflictContext {
    private ConflictStrategy strategy;

    public ConflictContext(ConflictStrategy strategy) {
        this.strategy = strategy;
    }

    public boolean check(CourseArrange arrange) {
        return strategy.hasConflict(arrange);
    }
}
```

优缺点：

- 优点：消除复杂条件判断；算法可以独立变化；新增规则时只新增策略类；符合 OCP、DIP；便于测试单个策略。
- 缺点：类数量增加；客户端或配置层需要知道使用哪种策略；策略之间如果有大量公共逻辑，需要再抽取公共父类或工具方法。

答题结构：

1. 先列优点：例如功能直接、逻辑可运行、分支覆盖了主要情况等。
2. 再列缺点：复杂条件、重复逻辑、魔法数字、命名不清、嵌套过深、异常处理不足、边界条件缺失、职责不清。
3. 再说明改进方法：提取方法、命名中间变量、减少嵌套、提前返回、使用表驱动、用数据结构消减判断、防御式检查、契约式设计。
4. 最后给改进代码，并说明改进后更易读、更可靠、更可维护。

高频改进方法：

- 提取方法：把复杂判断拆成含义明确的小方法。
- 命名中间变量：用变量名表达复杂条件的业务含义。
- 表驱动：用表、映射或数组替代大量 `if-else` / `switch`。
- 防御式编程：检查非法输入、空值、越界、异常情况。
- 契约式设计：明确前置条件、后置条件和不变式。
- 消除重复：把重复逻辑抽成公共方法或数据结构。
- 简化控制流：减少嵌套，使用提前返回。

## 第十大题：人机交互界面分析

状态：已确定放在第十大题，按 10 分界面分析题准备。

题目形式：

1. 给界面、截图、软件或系统页面。
2. 从人机交互原则角度分析。
3. 说明界面设计的优点和缺点。
4. 至少写 3 点或 5 点，按题目要求来。
5. 若分析缺点，要给出改进建议。

答题结构：

1. 先点出现象：界面中具体哪里好或不好。
2. 再写原则：对应可用性、精神模型、一致性、反馈、导航、错误预防、差异性、协作式设计等原则。
3. 再写影响：说明这个设计对用户理解、操作效率、错误率或满意度的影响。
4. 最后写改进：如果题目要求分析不足，要给出具体修改方案。

可套用句式：

该界面在某处体现/违反了某人机交互原则。具体表现为……这会使用户……因此它提升/降低了系统的可用性。改进时应当……。

常用原则准备：

- 可用性：易学性、效率、易记性、容错性、满意度。
- 精神模型：界面符合用户已有经验和操作预期。
- 一致性：相同功能、布局、术语和反馈方式保持一致。
- 反馈：用户操作后系统及时、明确地告知结果或状态。
- 导航：用户知道自己在哪里、能去哪里、如何返回。
- 错误预防与恢复：减少误操作，并帮助用户从错误中恢复。
- 差异性：重要信息、状态和可操作项要有清晰区分。
- 协作式设计：界面帮助用户完成任务，而不是让用户记忆系统内部细节。

往年出法演变：

1. `Exam/2013A.pdf`、`Exam/2013B.pdf`：给常见软件，不一定给截图；要求指出至少 3 条人机交互优点，并说明体现的原则。
2. `Exam/2016.pdf`、`Exam/2020.pdf`：给界面图或页面；要求说明体现了哪些人机交互原则，至少 3 点。
3. `Exam/2022.pdf`、`Exam/2025.pdf`：给系统页面或截图；要求从人机交互原则角度分析界面设计的优点和缺点，并给出建议。
