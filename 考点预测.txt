
考点预测

第一大题：名词解释 / 简答

第一问：软件工程
结论：确定考。
答题关键词：系统化、规范化、可量化；软件开发、运行、维护；工程化方法。

第二问：软件体系结构
答题关键词：软件系统的高层组织结构；部件、连接件、配置；体现重要设计决策并影响质量属性。

第三问：再工程与逆向工程
答题关键词：逆向工程是从已有系统中分析并恢复部件、关系、需求、架构或设计，重点是理解和抽象恢复；再工程是在理解旧系统基础上重构、迁移、重写或改造系统，目标是改善结构、质量、可维护性或适配新环境。区别：逆向工程侧重理解和恢复，再工程侧重改造和提升。



第二大题：需求获取与需求分类

预测题型：给业务场景，要求识别参与者和用例，并区分业务需求、用户需求、系统级需求，以及数据需求、质量需求、对外接口需求。

必写点：
1. 参与者：写业务用户、管理人员、外部系统或平台服务。
2. 用例：围绕用户目标命名，每个用例用一句话说明主要交互流程。
3. 需求层次：业务需求写组织目标；用户需求写用户任务；系统级需求写系统必须提供的具体行为、输入输出或约束。
4. 需求类型：数据需求写系统需要保存和维护的数据；质量需求写性能、可靠性、可用性、安全性等质量属性；对外接口需求写外部 API、协议、平台或系统对接。
5. 答题结构：每项都写“结论 + 场景依据”，不要只列名词。





第三大题：需求分析与建模

预测题型：给业务场景，要求建立或补全用例图、用例描述、概念类图、系统顺序图、状态图中的若干项。

重点顺序：概念类图最重要，系统顺序图次之；用例图用于识别参与者和系统功能，状态图用于生命周期明显的对象。

必写点：
1. 用例图：系统边界内画用例，边界外画参与者；用例名用动宾结构；用连线表示参与者使用的功能。
2. 用例描述：写 ID、名称、参与者、触发条件、前置条件、后置条件、正常流程、扩展流程；正常流程写成功路径，扩展流程写异常和分支。
3. 概念类图：从需求描述中提取业务名词作为概念类，补属性、关联和多重性；不要写 Controller、Service、Repository。
4. 系统顺序图：按时间从上到下画消息；重点画参与者、系统、外部系统之间的交互，不展开内部实现对象。
5. 状态图：选择订单、账户、图书等生命周期明显的对象；写清状态、事件、转换、初始状态和终止状态。





第四大题：体系结构设计

结论：重点按“分层包图 / 物理包图 + 层间接口声明”准备。

预测题型：给业务场景，要求画分层体系结构图 / 包图 / 物理包图，并写展示层与逻辑层、逻辑层与数据层之间的接口声明。

核心判断：重点是分层和 MVC；分层图要体现展示层、业务逻辑层、数据访问层，以及上层依赖下层、层间通过接口交互。

画图必写点：
1. 分层：展示层、业务逻辑层、数据访问层；Web 题还要体现客户端 / 浏览器、服务器端和数据库。
2. 包结构：按 Controller / Service / Repository 或 DAO / Domain 或 Entity 组织，指定业务模块要落到对应包中。
3. 接口：展示层依赖 Service Interface；Service Impl 依赖 Repository / DAO Interface；实现类实现对应接口。
4. 依赖方向：从展示层到逻辑层，再到数据访问层和数据库；不要画反向依赖或展示层直接访问数据库。
5. VO / PO：VO 用于展示层与逻辑层交互，只包含前端需要的数据；PO 用于逻辑层与数据层交互，对应持久化对象。
6. 物理关系：客户端通过 HTTP / REST / JSON 调用服务器端，服务器端再访问数据库。

接口声明必写点：
1. Service 接口按用户操作 / 用例步骤定义方法，写参数和返回值，不写实现。
2. Repository / DAO 接口按数据访问需要定义方法，如查询、保存、更新、删除。
3. 每个接口写包名、接口名、方法名、参数、返回值。
4. 可以写伪代码；不重点考 Spring Boot 注解和 Java 语法细节。





第五大题：详细设计

结论：重点按“Controller - Service - Repository 三层详细顺序图 + 职责分配 + 控制风格”准备。

预测题型：给具体功能场景，要求画详细设计顺序图，并说明各对象职责、控制风格以及如何应对业务规则变化。

画图必写点：
1. 详细顺序图要展开系统内部对象，不要只画“用户 -> 系统”。
2. 对象顺序通常为：用户 / 界面 -> Controller -> Service -> Domain / Policy / Strategy -> Repository / DAO -> Database / ExternalSystem。
3. Controller 接收请求、解析参数、调用 Service、返回结果。
4. Service 组织用例流程、控制事务、协调领域对象、策略对象和 Repository。
5. Repository / DAO 负责查询和保存数据，隐藏数据库细节。
6. Domain / Policy / Strategy 负责具体业务规则，例如优惠券折扣、支付方式、补货规则、积分规则。

控制风格必写点：
1. 集中式控制：流程集中在一个控制对象中，简单但容易让控制对象过胖。
2. 分散式控制：流程分散到多个对象中，局部职责独立，但整体流程不易追踪。
3. 委托式控制：Controller 保留主流程，把具体业务委托给 Service、领域对象、策略对象和 Repository；业务系统优先按委托式写。

GRASP 落点：
1. Controller：用 Controller 接收系统事件。
2. Information Expert：把职责分给掌握所需信息的对象。
3. Low Coupling：Controller 不直接访问数据库，Service 依赖 Repository 接口。
4. High Cohesion：Controller、Service、Repository、领域对象各自只做本层职责。
5. Creator：由合适对象创建记录、订单、支付记录等业务对象。




第六大题：代码结构分析与设计原则

结论：重点按“比较代码好坏 + 识别违反的类设计原则 + 分析耦合与内聚 + 给出改进结构”准备。包原则不考。

预测题型：给出同一功能的两段简短代码，或给出一段存在设计问题的代码，要求判断代码好坏，指出违反的设计原则，从耦合、内聚和信息隐藏角度说明原因，并给出改进方案。题目明确要求时，再写简短接口、类结构、伪代码或改良代码，不需要写完整可运行程序。

最高优先原则：
1. SRP 单一职责原则：一个类只有一个变化原因；业务、持久化、通知、界面等职责不要混在一个类中。
2. OCP 开闭原则：对扩展开放、对修改关闭；新增业务类型时应增加实现类，不应反复修改 if-else 或 switch。
3. DIP 依赖倒置原则：高层业务模块和低层实现都依赖抽象；Service 不直接依赖具体数据库、DAO、文件或第三方客户端。
4. 面向接口编程：变量、参数和成员优先依赖接口，不依赖具体实现类，以便替换、测试和扩展。
5. 信息隐藏：隐藏字段、集合、内部对象、存储格式和变化的业务规则，只通过稳定接口访问。
6. 迪米特法则：只与直接对象交互，避免 a.getB().getC().doSomething() 形式的消息链。
7. 高内聚、低耦合：类内部职责应集中，类之间应减少对具体实现和内部结构的依赖。

其他需要掌握：
1. LSP 里氏替换原则：子类必须能够替换父类而不破坏程序正确性；不合理继承改用接口或组合。
2. ISP 接口隔离原则：接口只包含调用方需要的方法，避免实现类被迫实现无关方法。
3. 组合优于继承：优先通过持有对象和接口协作复用功能，避免继承具体类带来的强耦合。
4. 为变更而封装：将容易变化的算法、规则、创建方式或数据格式放入独立对象。
5. 权限最小化：字段和辅助方法优先 private，只开放必要接口。
6. DRY：同一业务规则不要在多处重复编码。
7. SOFA：方法要短、只做一件事、参数少、抽象层次一致。

耦合与内聚重点：
1. 控制耦合：调用方传入类型码、布尔值或标志，被调用方法根据该值使用 if-else 或 switch 选择行为；改为多个明确方法或多态 / 策略对象。
2. 印记耦合：传入整个对象或数据结构，但方法只使用其中少数字段；改为只传必要数据、使用专用参数对象，或把行为移动到拥有数据的对象中。
3. 低内聚：一个类或方法混合多个无关职责；改为按变化原因拆分类或提取方法。

固定答题结构：
1. 先给结论：哪段代码更好，或代码存在什么问题。
2. 点名原则：写出违反或符合的具体原则。
3. 对应代码现象：指出具体类、方法、字段、依赖或条件分支。
4. 说明危害：高耦合、低内聚、修改扩散、内部结构暴露、难测试或难扩展。
5. 给出改法：拆分类、提取接口、依赖注入、封装字段、移动职责、使用组合，或用多态替代条件分支。
6. 题目要求代码时，写能体现职责和依赖方向的简短代码；只要求分析时，不必展开完整实现。




第七大题：设计模式 / 策略模式

结论：重点按“变化规则场景 + 策略接口 + 具体策略 + Context / Service + 原则说明”准备。工厂方法和抽象工厂按对象创建或 DAO 切换的补充辨析准备。

预测题型：给业务规则会变化的场景，要求识别变化点，设计类结构，使新增规则时不修改原有主流程。场景可能是课程冲突检测、积分计算、优惠券、支付方式、订货规则等。

变化点判断：
1. 冲突检测、积分计算、优惠券计算、支付处理等属于算法 / 业务规则变化点。
2. 变化的不是主流程，而是具体规则如何执行。
3. 主流程应保持稳定，变化规则应封装到独立策略类中。

策略模式必写结构：
1. Strategy 接口：定义统一算法入口，例如 check(context)、calculate(context)、pay(command)、discount(amount)。
2. ConcreteStrategy：每一种规则、支付方式、优惠券或冲突检测写一个具体实现类。
3. Context / Service：持有 Strategy 接口或 Strategy 列表，只调用接口，不依赖具体策略类。
4. Client / 配置层：负责选择、注入或组合具体策略。
5. 新增规则时新增具体策略类，并加入配置或策略集合，不修改原有主流程。

课程冲突检测答题模板：
1. 定义 ConflictCheckStrategy 接口，声明 check(ScheduleContext context)。
2. 定义 TeacherConflictCheckStrategy、ClassroomConflictCheckStrategy、StudentConflictCheckStrategy 等具体策略。
3. 定义 ConflictCheckService，持有 List<ConflictCheckStrategy>，遍历调用每个策略的 check 方法。
4. 新增班级冲突、考试冲突等规则时，只新增新的策略类，不修改 ConflictCheckService 主流程。

必写原则：
1. OCP 开闭原则：新增规则通过新增策略类完成，不修改主流程。
2. DIP 依赖倒置原则：主流程依赖 Strategy 接口，不依赖具体策略实现。
3. SRP 单一职责原则：每个策略类只负责一种规则。
4. 高内聚、低耦合：规则逻辑集中在对应策略类中，主流程与具体规则解耦。
5. 为变更而封装：把容易变化的算法和业务规则封装为独立对象。

优缺点：
1. 优点：减少 if-else / switch，扩展规则方便，规则之间互不影响，主流程稳定。
2. 缺点：类数量增加；客户端、配置层或 Context 需要知道使用哪些策略。

与工厂方法 / 抽象工厂辨析：
1. 题目问“选择不同算法 / 业务规则 / 计算方式 / 检测方式”，答策略模式。
2. 题目问“把对象创建延迟到子类，决定创建哪一个具体对象”，答工厂方法。
3. 题目问“创建一组配套对象 / DAO 产品族，例如 MySQL DAO 与 SQLServer DAO 整套替换”，答抽象工厂。
4. 不要只写“工厂模式”，应明确写工厂方法或抽象工厂。




第八大题：软件构造与代码改进

结论：重点按“坏代码分析 + 构造质量问题 + 改进方法 + 改良代码或伪代码”准备。与第六大题相比，本题更偏代码本身的可读性、可维护性、可靠性和控制结构。

预测题型：给一段 Java 方法或伪代码，要求从软件构造角度分析优缺点，指出代码问题，并写出改进后的代码或伪代码。

常见代码材料：
1. 区间规则代码：按金额、天数、年龄、等级返回结果，例如税率、月份天数、订货天数、积分规则。
2. 复杂布尔表达式：一行代码中堆叠多个 &&、|| 和取反条件。
3. 多层嵌套判断：if-else 嵌套过深，正常路径和异常路径混在一起。
4. Web / Controller 方法：Controller 中直接写业务校验、数据访问、字符串响应和异常处理。
5. 错误返回值：用 -1、null、"yes"、"no"、状态字符串表示错误或结果。

问题识别：
1. 可读性问题：方法名、变量名无意义；条件表达式过长；布尔逻辑难读；代码格式混乱。
2. 可维护性问题：魔法数字、硬编码字符串、重复逻辑、边界值分散、规则写死在控制结构中。
3. 可靠性问题：没有处理 null、非法输入、边界值、异常；吞掉异常；返回哨兵值导致调用方误用。
4. 控制结构问题：嵌套过深、长 if-else / switch、重复循环、过长返回表达式。
5. 职责问题：一个方法同时负责参数读取、业务判断、数据访问、结果输出或异常处理。

改进方法：
1. 清晰命名：方法名和变量名要表达业务含义。
2. 提取方法：把复杂判断拆成有语义的小方法。
3. 命名条件：用中间变量或方法名解释复杂布尔表达式。
4. 表驱动：用数组、Map 或规则表替代长分支。
5. 提前返回：先处理非法输入和异常路径，减少嵌套。
6. 防御式检查：检查 null、非法输入、越界值和缺失规则。
7. 规则对象化：规则较复杂或经常变化时，把规则封装成独立对象。
8. 分层改造：Controller 只处理请求和响应，Service 处理业务规则，Repository / DAO 处理数据访问。

区间规则题答法：
1. 指出问题：魔法数字、边界不清、漏掉区间、非法输入未处理、分支重复。
2. 改进方式：优先写清楚边界和非法输入；规则数量多时使用表驱动或规则对象。
3. 代码要体现：输入检查、边界覆盖、规则清晰、默认异常路径。

复杂布尔表达式题答法：
1. 指出问题：一行表达式过长，条件含义不清，修改和测试困难。
2. 改进方式：提取中间变量或小方法，让每个条件表达业务含义。
3. 示例结构：return teacherAvailable(request) && classroomAvailable(request) && studentsAvailable(request) && timeSlotValid(request)。

Web 方法题答法：
1. 指出问题：Controller 混入业务逻辑和 DAO 调用，直接返回字符串，异常处理弱，参数名和响应语义不清。
2. 改进方式：Controller 调用 Service，Service 校验业务规则，Repository / DAO 负责读写数据，返回结构化结果。
3. 不需要写完整 Spring Boot 注解，重点写清职责分离和调用方向。

固定答题结构：
1. 先写优点：能完成基本功能，有基本输入输出或基本成功失败流程。
2. 再写缺点：从可读性、可维护性、可靠性、控制结构、职责划分中选至少三点。
3. 说明影响：难理解、难修改、难测试、边界错误、异常路径不明确。
4. 给出改法：提取方法、命名条件、表驱动、提前返回、防御式检查、规则对象化、分层拆分。
5. 写改良代码或伪代码：代码不必完整可运行，但必须体现清晰命名、边界处理和主要改进结构。




第九大题：软件测试 / 文字测试用例

结论：重点按“给业务场景 + 选择黑盒测试方法 + 设计文字测试用例表”准备。67 录音没有展开软件测试考法，本题主要依据往年卷和考点清单判断。

预测题型：给一个业务功能或业务规则，要求选择适当的测试用例设计方法，并设计不少于若干条测试用例。测试用例应写清输入、操作步骤、预期结果和覆盖点。

最可能场景：
1. 修改密码：用户存在、旧密码、新密码合法性、两次密码一致、新旧密码相同、连续错误锁定。
2. 预约 / 选课：资格、时间冲突、容量、重复预约、取消、状态变化。
3. 充值 / 支付 / 优惠券：金额边界、支付方式、优惠券有效性、过期、门槛、重复使用。
4. 订单 / 设备 / 图书：状态转换、库存或数量边界、权限、异常输入。
5. 订货规则 / 费用计算：数值边界、非法输入、缺失区间、规则分支。

方法选择：
1. 等价类划分：用于合法输入、非法输入、不同业务状态。
2. 边界值分析：用于金额、数量、年龄、天数、时间、容量等有范围的数据。
3. 决策表：用于多个条件组合决定结果的场景，例如优惠券是否有效、金额是否达标、是否会员、是否过期。
4. 状态转换：用于对象状态变化明显的场景，例如订单、预约、账户、设备申请。
5. 如果题目给代码，再考虑圈复杂度、条件覆盖、分支覆盖；但文字测试用例优先按黑盒方法写。

测试用例表格格式：
编号 | 测试场景 | 输入 / 前置条件 | 操作步骤 | 预期结果 | 覆盖点

必覆盖内容：
1. 正常成功路径：至少一条有效输入能成功完成业务。
2. 非法输入：空值、格式错误、越界值、不存在对象。
3. 边界值：最小值、最大值、边界内、边界外。
4. 业务规则失败：条件不满足、资格不足、余额不足、库存不足、优惠券不可用。
5. 状态异常：重复提交、已取消后再操作、已完成后再修改、锁定状态下操作。
6. 异常结果：应写清系统提示、拒绝操作、保持原状态或抛出异常。

固定答题结构：
1. 先说明采用的方法：等价类划分、边界值分析；有状态变化时补状态转换；多条件组合时补决策表。
2. 再说明测试维度：合法 / 非法、边界、状态、异常、业务规则。
3. 用表格列测试用例，每条必须有输入或前置条件、操作步骤、预期结果。
4. 不要只写“测试旧密码错误”这种测试点，要写成可以执行的测试用例。
5. 预期结果要具体，例如“提示旧密码错误，密码不被修改”，不要只写“失败”。

修改密码示例：
1. 正常修改：用户存在，旧密码正确，新密码合法且两次一致；提交修改；预期修改成功。
2. 旧密码错误：用户存在，旧密码错误；提交修改；预期提示旧密码错误，密码不变。
3. 用户不存在：输入不存在的用户名；提交修改；预期提示用户不存在。
4. 新密码太短：新密码长度低于最小限制；提交修改；预期提示密码不合法。
5. 两次新密码不一致：new1 与 new2 不同；提交修改；预期提示两次密码不一致。
6. 新密码与旧密码相同：old 与 new 相同；提交修改；预期提示新旧密码不能相同。




第十大题：人机交互界面分析

结论：重点按“界面现象 -> 人机交互原则 -> 用户影响 -> 改进建议”准备。67 录音明确说人机交互原则不需要背得特别准确，但要能从界面中看出哪里好、哪里不好，并说明理由。

预测题型：给一张业务系统界面或常见软件界面截图，要求从人机交互原则角度分析界面设计的优点和不足，并提出改进建议。

固定答题结构：
1. 写优点：至少 2 点，每点说明界面现象、体现的原则和对用户的好处。
2. 写不足：至少 3 点，每点说明界面现象、违反或弱化的原则、对用户的影响。
3. 写改进：每个不足对应一个可执行改法，不要只写“优化界面”。
4. 每一点都按“现象 -> 原则 -> 影响 -> 改进建议”展开。

常用原则：
1. 系统状态可见：页面应显示当前状态、处理进度、成功失败结果、余额、库存、订单状态等。
2. 识别优于回忆：金额、日期、数量、规则、对象、状态应直接展示，减少用户记忆负担。
3. 一致性：术语、按钮名称、颜色、位置、图标和操作流程要保持一致。
4. 错误预防：危险操作隔离，提交前说明后果，不可用操作禁用，高风险操作二次确认。
5. 用户控制与自由：允许取消、返回、撤销、修改，误操作后有恢复入口。
6. 反馈明确：操作后给出成功、失败、失败原因和下一步恢复方式。
7. 灵活性和效率：常用操作便捷，支持快捷入口、筛选、默认值或批量操作。
8. Fitts 定律：常用按钮靠近操作对象，危险按钮不要紧贴主按钮。
9. 可用性：界面应易学、高效、易记、少出错、可恢复、让用户满意。

常见界面问题：
1. 按钮语义不明确：例如“确定”“提交”“执行”“订”过短或不说明后果。
2. 状态反馈不足：提交后不知道是否处理中、是否成功、失败原因是什么。
3. 危险操作太突出或离主操作太近：例如删除、取消、挂失和确认按钮并列。
4. 业务规则隐藏：优惠规则、取消规则、审核规则、时间限制、余额限制没有显示。
5. 数值和时间缺少上下文：金额没有单位或范围，日期缺少年份、星期、晚数或时间段。
6. 错误预防不足：明知有冲突、超时、库存不足或权限不足，仍允许提交。
7. 隐私暴露：卡号、地址、手机号、支付信息等敏感信息没有遮挡或确认。
8. 恢复入口缺失：支付失败、预约失败、订单取消、网络错误后没有重试或返回入口。

高频场景关注点：
1. 充值 / 支付界面：金额范围、单位、最终金额、支付状态、失败恢复、敏感信息遮挡。
2. 预约 / 选课界面：时间冲突、容量、资格、审核状态、取消规则、返回后保留筛选条件。
3. 订单 / 预订界面：地址、价格明细、优惠规则、取消风险、预计送达或入住时间、删除或取消确认。
4. 后台管理界面：导航位置、列表筛选、操作对象、批量操作、执行后果、异常数据提示。

答题模板：
1. 优点：界面将余额、充值记录和操作入口放在同一页面，用户能直接识别当前账户状态和可执行任务，体现系统状态可见和识别优于回忆，提高操作效率。
2. 不足：删除订单与去支付按钮并列且视觉权重接近，危险操作容易被误点，违反错误预防原则；应降低删除按钮权重，拉开位置，并增加二次确认。
3. 不足：提交失败后只显示失败，没有说明失败原因和恢复方式，反馈不足；应明确提示原因，例如余额不足、库存不足或网络失败，并提供重试或修改入口。
